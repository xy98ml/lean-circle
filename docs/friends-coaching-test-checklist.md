# 好友减脂协作系统验收清单

> 数据库迁移维护约定：`supabase-ai-menu-schema.sql` 是 AI/菜单扩展的 canonical 来源；`supabase-friends-schema.sql` 的同名标记段由其事务体同步。独立迁移自行使用 `BEGIN/COMMIT`，主迁移只复制事务体并由主文件最外层事务包裹。每次修改后必须做规范化内容比较，禁止手工维护两份不同逻辑。

## 1. 数据库与账号

- [ ] 已执行 `supabase-schema.sql`。
- [ ] 已执行 `supabase-friends-schema.sql`，没有 SQL 错误。
- [ ] 如果项目已执行过旧版好友迁移，已再执行 `supabase-ai-menu-schema.sql`，没有 SQL 错误；全新项目只需执行同步后的 `supabase-friends-schema.sql`。
- [ ] 在无新增业务写入的情况下重复执行对应迁移，第二次仍成功且没有生成重复约束、策略或函数重载。
- [ ] `member_profile_versions`、`menu_submissions`、`menu_assignments` 均已启用 RLS。
- [ ] `plan_versions` 已包含脂肪、碳水、膳食纤维和计算方法字段，且都为非空。
- [ ] 管理员邮箱已注册并完成确认。
- [ ] 已替换并执行 `supabase-make-admin.sql`，查询结果只有预期管理员。
- [ ] 网页中不存在 `service_role`、`sb_secret_...` 或数据库密码。

## 2. 管理员流程

- [ ] 普通账号打开 `admin.html` 时显示拒绝访问，无法看到成员数据。
- [ ] 管理员登录后可以看到成员、待设计、计划和近 7 天记录指标。
- [ ] 可以创建单次邀请，复制的链接包含 `join.html?invite=`。
- [ ] 可以停用未使用的邀请，停用后朋友无法加入。
- [ ] 可以查看成员问卷和最近 14 条记录。
- [ ] 发布计划时必须填写调整原因。
- [ ] 每次发布都会新增版本，旧版本仍可查看。
- [ ] 管理员可以查看自己邀请且仍有效的成员资料历史与菜单提交，不能查看其他管理员的成员。
- [ ] AI 计划的热量最低值低于成员 BMR 时，发布被拒绝。
- [ ] AI 计划的宏量营养换算与热量目标明显不一致时，发布被拒绝。
- [ ] `publish_member_bundle` 可以只发布计划，不要求同时下发菜单。
- [ ] 同时发布计划和菜单时，两者在一次操作中一起成功；任意一项校验失败时均不新增记录。
- [ ] 使用同一个 `client_request_id` 连续或并发请求两次，只生成一个计划版本和至多一个菜单版本，第二次返回第一次的 ID 与版本。
- [ ] 同一个 `client_request_id` 改用于另一位成员时被拒绝，不会读取或覆盖原发布结果。
- [ ] 菜单下发必须属于目标成员；使用其他成员的提交 ID 时被拒绝。
- [ ] 菜单发布后原提交状态变为 `published`，且不能再由成员修订。
- [ ] 管理员不能绕过 `publish_member_bundle` 直接向 `plan_versions` 或 `menu_assignments` 写入。
- [ ] 管理台没有修改或删除成员每日记录的入口。

## 3. 成员加入流程

- [ ] 没有邀请令牌时，`join.html` 明确提示需要有效邀请。
- [ ] 新成员可以注册；启用邮箱确认时，页面会提示先确认邮箱。
- [ ] 有效邀请登录后会显示完整问卷。
- [ ] 新成员提交入组时只调用一次 `submit_member_onboarding`，并将 URL 中的邀请令牌作为 `invite_token` 参数一起提交；前端不再调用 `accept_coach_invite`。
- [ ] 故意让入组资料、风险字段或自动计划校验失败后，邀请 `use_count` 不增加，也不会留下 `coach_memberships` 记录。
- [ ] 同一新成员并发提交两次入组请求时，只消耗一次邀请；资料历史版本与计划版本保持连续。
- [ ] 已加入成员再次更新资料时复用现有有效 membership，不重复消耗邀请次数。
- [ ] 年龄小于 18 岁不能提交。
- [ ] 未勾选授权确认不能提交。
- [ ] “快速套用”会生成第一版计划并在个人面板显示。
- [ ] 快速套用使用“视频公式 + BMR 安全下限”，并同时生成热量、蛋白质、脂肪、碳水和膳食纤维目标。
- [ ] 使用 35 kg、150 cm、29 岁女性等合法低体重边界数据时，自动计划 `calories_min` 仍不低于数据库要求的 1000 kcal。
- [ ] “个性化设计”会进入管理员待处理列表。
- [ ] 安全筛查命中时不会自动生成普通减脂计划。
- [ ] 风险字段缺省时按 `false` 处理；传入 `"false"`、`0`、`null`、对象或数组等非 JSON boolean 类型时整次提交失败且不写入资料快照。
- [ ] 曾因风险筛查暂停的计划，在风险解除并重新提交无风险“快速套用”后新增版本且恢复为 `active`。
- [ ] 首次提交资料后生成 `member_profile_versions` 第 1 版；再次提交后保留第 1 版并新增第 2 版。
- [ ] 成员可以提交自己的周菜单，也可以在发布前修订自己的提交。
- [ ] 成员不能修订已发布菜单，也不能指定或修改其他成员的提交 ID。
- [ ] 菜单 `week_start` 不是周一时，`submit_member_menu` 拒绝整个请求。
- [ ] 菜单 `days` 缺失、不是数组、为空或超过 7 天时被拒绝。
- [ ] 菜单日期非法、超出所选周、同一天重复出现时被拒绝。
- [ ] 菜单包含未知日字段、未知餐字段、重复餐次，或餐次不是“早餐/午餐/晚餐”时被拒绝。
- [ ] 候选菜不是字符串、为空、超过 200 字、单餐超过 30 项，或整份菜单没有候选菜时被拒绝。
- [ ] 日标签超过 40 字、餐次备注超过 500 字、提交备注超过 4000 字时被拒绝。
- [ ] 上述畸形菜单均通过直接 RPC 调用验证，失败后没有新增或修改 `menu_submissions`。
- [ ] 已停用、过期或用完的邀请会显示对应错误。

## 4. 数据隔离与同步

- [ ] 成员 A 无法通过页面或 Supabase API 读取成员 B 的资料、问卷、计划和日志。
- [ ] 成员 A 无法读取成员 B 的资料历史、菜单提交或菜单下发记录。
- [ ] 管理员可以读取 A、B 的数据。
- [ ] 普通成员对资料历史和菜单表没有直接新增、修改或删除权限；合法写入只能通过对应 RPC。
- [ ] 匿名账号无法读取资料历史、菜单提交和菜单下发记录，也不能执行提交或发布 RPC。
- [ ] 管理员尝试更新或删除成员 `daily_logs` 时被 RLS 拒绝。
- [ ] 成员可以新增、修改和删除自己的每日记录。
- [ ] 同一账号在两台设备登录后可以同步记录和菜单。
- [ ] 成员只看到管理员下发给自己的菜单；管理员下发给 A 的菜单不会出现在 B 的账号中。
- [ ] 同一浏览器从账号 A 退出后登录账号 B，不会显示 A 的本地记录、菜单或计划目标。
- [ ] 离线保存后恢复网络，记录可以同步到云端。
- [ ] 第二天补记时，记录归档到实际发生日期。

## 5. 页面与部署

- [ ] `index.html` 能进入个人面板。
- [ ] GitHub Pages 上个人面板、加入页和管理台均能直接打开。
- [ ] Supabase Site URL 和 Redirect URLs 已加入线上域名。
- [ ] 手机上表格可横向滚动，表单无明显溢出。
- [ ] 浅色和深色模式下文字、按钮和状态标签均清晰。
- [ ] 刷新线上邀请页后，邀请令牌仍保留在 URL 中。

## 6. 上线前最终检查

- [ ] 用一个管理员账号和两个普通账号完整走通一次。
- [ ] 运行迁移文件末尾的只读验证查询，核对新表 RLS、新列、SECURITY DEFINER RPC 与策略名称。
- [ ] 只读验证覆盖所有协作表及原有个人数据表，并确认旧 `publish_member_plan` 与 `accept_coach_invite` 函数数量均为 0。
- [ ] 核对 `submit_member_menu`、`publish_member_bundle` 等函数已撤销 `public`/`anon` 执行权，并仅向 `authenticated` 授权。
- [ ] 确认前端仓库和静态资源中没有真实菜名、成员身体数据或 AI 密钥。
- [ ] 删除测试账号或明确标记测试数据，避免和真实成员混淆。
- [ ] 只分享管理员刚生成的线上邀请链接。
- [ ] 告知成员这不是医疗诊断工具；出现异常症状时优先就医。
